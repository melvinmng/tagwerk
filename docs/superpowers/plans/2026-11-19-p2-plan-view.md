# P2 Planen-Ansicht: aktuelle Uhrzeit, mitziehbare Seiten, Fahrzeit – Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Status:** Entwurf vom 19.11.2026, ohne Mockups (Designrunde folgt in #188). Nichts gebaut, nichts am Gerät geprüft. Grundlage ist `main` auf `70a2b9c`.

**Goal:** In „Planen“ zeigt die Tagesansicht von heute die aktuelle Uhrzeit im Ablauf (#157). Tage und Wochen in „Planen“ und „Erfassen“ lassen sich als Seiten blättern, die beim Wischen den Nachbarn mitziehen (#134). Termine mit Ort bekommen einen Fahrzeit-Abschnitt davor, und Kapazität und KI-Planung rechnen damit (#168).

**Architecture:**
- Reine Regeln liegen in `TagwerkCore`: `NowMarker`, `TravelRules` sowie die Erweiterungen von `CapacityInput` und `PlanInputDay`.
- Die App bekommt diese neuen Bausteine:
  - Ansichten: `NowLine`, `PagedContainer` und `TravelSegmentView`.
  - Fahrzeit: ein `TravelTimeService` (MapKit, mit Datei-Cache) und eine Einstellungsseite `TravelSettingsView`.
- Bestehende Ansichten bekommen jeweils nur einen kleinen, gekapselten Eingriff. Das gilt für `TimelineCanvas`, `DayGridScreen`, `DayView`, `WeekView`, `CaptureView`, `WeekReviewView`, `EntrySheet` und `PlanningSettingsSection`.

**Tech Stack:** Swift 6, SwiftUI (iOS 27), SwiftData (nur `AppSettings`), MapKit (`MKDirections`, `MKGeocodingRequest`), EventKit, Swift Testing, XcodeGen.

**Issues:** #157, #134, #168. Branch: `feat/plan-view-now-paging-travel`.

## Task 0: Spike #134 – Technik für mitziehbare Seiten (max. 2 h)

**Frage:** Welche Technik zieht den Nachbartag beim Wischen sichtbar mit, ohne dass die bestehenden Gesten kaputtgehen? Bestehende Gesten sind: senkrechtes Scrollen in `List` und im `DayGridScreen`-ScrollView, Halten und Ziehen von Blöcken (`HoldToMoveRecognizer`, UIKit), Ziehen aus „Ohne Uhrzeit“, Kontextmenüs, die System-Zurückgeste in `WeekReviewView` und `.refreshable`.

**Varianten:**
- **A:** `ScrollView(.horizontal)` mit drei Seiten `[anker−1, anker, anker+1]`, `.scrollTargetBehavior(.paging)` und `.scrollPosition(id:)`. Ist eine Nachbarseite eingerastet, wird `model.step` aufgerufen und ohne Animation auf die Mitte zurückgesetzt.
- **B:** Ein eigener `PagedContainer` mit `DragGesture` als `simultaneousGesture`.
  - Er übernimmt die Richtungsregel aus `PageSwipe.direction`: Ab etwa 12 pt seitlich und mindestens doppelt so weit seitlich wie senkrecht folgt der Inhalt dem Finger (`offset`). Die Nachbarseite liegt daneben.
  - Beim Loslassen blättert er, wenn die Schwelle oder `predictedEndTranslation` erreicht ist. Sonst federt er zurück.
  - Ist der Inhalt gesperrt (`isDragging` im Raster), passiert gar nichts.

## Task 5: `TravelRules` in TagwerkCore (#168)

**Files:**
- Create: `app/Packages/TagwerkCore/Sources/TagwerkCore/TravelRules.swift`
- Test: `app/Packages/TagwerkCore/Tests/TagwerkCoreTests/TravelRulesTests.swift`

**API:**
```swift
public enum TravelTransport: String, Sendable, CaseIterable, Codable { case automobile, transit, walking, cycling }

public struct TravelPlace: Sendable, Hashable, Codable {
    public var text: String            // as typed in the event or settings
    public var latitude: Double?       // from the event's structured location, if any
    public var longitude: Double?
    /// Stable key for the cache: rounded coordinates when known, else the normalised text.
    public var key: String
}

public struct TravelLeg: Sendable, Hashable {
    public enum Origin: Sendable, Hashable { case previousEvent(id: String), home }
    public var eventID: String
    public var origin: Origin
    public var from: TravelPlace
    public var to: TravelPlace
    public var arrival: Date           // event start
}

public struct TravelSegment: Sendable, Hashable, Identifiable {
    public var id: String { eventID }
    public var eventID: String
    public var range: Range<Int>       // minutes of the day, ending at the event start
    public var minutes: Int
    public var origin: TravelLeg.Origin
    /// Travel starts before the previous event ends.
    public var isTight: Bool
}

public enum TravelRules {
    public static let homeGapMinutes = 180   // longer gaps: the trip starts at home
    public static func isPhysicalLocation(_ text: String) -> Bool
    public static func legs(events: [CalendarEvent], on day: PlanDay, home: TravelPlace?, calendar: Calendar) -> [TravelLeg]
    public static func segments(legs: [TravelLeg], minutes: [String: Int], events: [CalendarEvent],
                                on day: PlanDay, calendar: Calendar) -> [TravelSegment]
    /// Rounds an ETA up to 5 minutes; 0 when under 3 minutes.
    public static func roundedMinutes(seconds: Double) -> Int
}
```

**Regeln (alle getestet):**
1. Nur getaktete, belegte Termine (`isBusy`, nicht ganztägig) mit physischem Ort bekommen eine Strecke. Leerer Ort, URL, „Zoom“, „Teams“, „Webex“, „Google Meet“, „Online“ und „FaceTime“ zählen nicht, ohne Rücksicht auf Groß- und Kleinschreibung.
2. **Ausgangspunkt:**
   - Normalfall ist der nächste vorherige Termin desselben Tages mit physischem Ort, der vor dem Start dieses Termins endet.
   - Liegt dazwischen mehr als `homeGapMinutes` oder gibt es keinen vorherigen Termin mit Ort: die Heimadresse.
   - Ohne Heimadresse in diesem Fall: keine Strecke.
3. Gleicher Ort (gleicher `key`) als Start und Ziel ergibt keine Strecke.
4. Zum Ziel Heimadresse (Termin „zu Hause“ mit gleichem key wie home) mit Ausgangspunkt home gibt es keine Strecke.
5. Ein Segment ist `(start − minutes)..<start`, abgeschnitten auf 0. `isTight` gilt, wenn das Segment vor dem Ende des Ausgangstermins beginnt.
6. Fehlt für eine Strecke der Wert in `minutes`, gibt es kein Segment (offline oder noch nicht geladen).
7. Termine, die mit einer Aufgabe verknüpft sind (Blöcke), bekommen nur dann eine Strecke, wenn sie einen Ort haben. Sie dienen auch als Ausgangspunkt.

## Task 8: `TravelTimeService` mit Cache und Heimadresse (#168)

**Files:**
- Create `app/Tagwerk/Planning/TravelTimeService.swift`:
  - `protocol TravelTimeEstimating: Sendable { func minutes(from: TravelPlace, to: TravelPlace, transport: TravelTransport, arrival: Date) async throws -> Int }`
  - Die Umsetzung `MapKitTravelEstimator` nutzt `MKDirections.Request` mit `transportType` und `arrivalDate` und dann `calculateETA()`.
    - Ziel und Start ohne Koordinaten werden über `MKGeocodingRequest` aufgelöst (iOS 26+ API). Die Ergebnisse liegen im Cache.
    - `.cycling` nur, wenn `MKDirectionsTransportType` es auf iOS 27 anbietet. Sonst die Option ausblenden.
  - `@MainActor @Observable final class TravelTimeService`:

## Spike-Ergebnis #134

**Entscheidung:** Variante B, aber mit einem UIKit-Pan-Recognizer statt einer SwiftUI-`DragGesture` (Variante „C“ im Spike). Variante A (waagrechter Paging-`ScrollView`) entfällt.

**Vorgehen:** Wegwerf-Code in `DayView` (Raster und Liste), `CaptureView` und `WeekReviewView`, dazu ein wegwerfbarer UI-Test (XCUITest) im eigenen Simulator mit `-TagwerkDemoData`. Der Code schrieb Messwerte in eine Sonde (größter seitlicher Versatz, Anzahl Blättervorgänge), die der Test ausliest. Alle drei Varianten liefen gegen dieselben 12 Szenarien. Der Wegwerf-Code ist verworfen.

| Szenario | A: Paging-ScrollView | B: SwiftUI-`DragGesture` | C: UIKit-Pan (gewählt) |
|---|---|---|---|
| Senkrechtes Scrollen, auch mit 15 pt seitlich | kein Blättern | kein Blättern | kein Blättern |
| Langsames kurzes Ziehen (50 pt) folgt dem Finger und federt zurück | Sonde sah keinen Versatz (Messung unsicher) | ja (50 pt) | ja (40 pt) |
| Schnelles Wischen blättert (Raster) | blätterte im Raster nicht, in der Liste schon | ja | ja |
| Diagonales Ziehen (100/140 pt) | kein Blättern | kein Blättern | kein Blättern |
| Block halten und seitlich ziehen | kein Blättern | kein Blättern, Versatz 0 | kein Blättern, Versatz 0 |
| Block halten und eine Stunde nach unten ziehen | **Block bewegte sich nicht** | verschoben | verschoben |
| Aufgabe aus „Ohne Uhrzeit“ ins Raster ziehen | kein Blättern | kein Blättern | kein Blättern |
| Kontextmenü in der Liste (Halten 1,2 s) | Menü erscheint | Menü erscheint | Menü erscheint |
| Ziehen nach unten am Anfang (Pull-to-refresh) | kein Blättern | kein Blättern | kein Blättern |
| Doppelwischen | 2 Seiten | 2 Seiten (mit Nachbesserung, siehe unten) | 2 Seiten |
| „Erfassen“ auf heute nach vorn | blätterte auf eine Seite in die Zukunft (kein Sperren möglich) | Gummiband, kein Blättern | Gummiband, kein Blättern |
| Wochenrückblick: Rückgeste vom linken Rand | ging zurück, aber doppelte Zählung beim Blättern | ging zurück | ging zurück |
| Wisch beginnt auf einer Schaltfläche (Kapazitätskarte) | kein Blättern | blättert **und löst die Schaltfläche aus** (Blatt „Arbeitszeit“ öffnet sich) | blättert, Schaltfläche bleibt unberührt |

**Begründung:**
- **A** scheitert an den Gesten, die der Plan nennt: Das Halten und senkrechte Ziehen eines Blocks verschob den Block nicht. Auf heute lässt sich in „Erfassen“ die Zukunftsseite nicht sperren, weil der `ScrollView` sie anbietet. Außerdem zählte das Zurücksetzen der Position mehrfach (Wochenrückblick: 3 statt 1 Blättervorgang je Wisch). Der Neustart auf die Mitte erzeugt zusätzliche Zustandswechsel, und alle drei Seiten bräuchten vollständigen Zustand.
- **B mit `DragGesture`** erfüllt die Richtungsregel, hat aber einen Fehler: Folgt der Inhalt dem Finger, bleibt die Schaltfläche unter dem Finger und löst beim Loslassen aus. Im Test öffnete sich das Arbeitszeit-Blatt, obwohl die Seite blätterte. `simultaneousGesture` bricht die Berührung der Kinder nicht ab.
- **C** beginnt nur bei überwiegend seitlicher Bewegung (`gestureRecognizerShouldBegin`) und bricht die Berührungen des Inhalts ab (`cancelsTouchesInView`). Damit löst kein Button mehr aus. Ein senkrechter `ScrollView` und die Halte-Geste kollidieren nicht, weil ein senkrechter `ScrollView` seitliche Bewegungen nicht beansprucht und die Sperre (`isLocked`) in `shouldBegin` greift. Die Plan-Vorgabe „B, wenn gleich gut“ gilt damit, aber mit anderem Recognizer.
- **Doppelwischen:** Eine erste Fassung von B wartete auf das Ende der Animation, bevor die Seite wechselte. Dabei ging das zweite Wischen verloren (nur 1 Seite). Die Lösung: Der Seitenwechsel läuft, wenn die Animation endet oder sobald die nächste Geste beginnt (`pendingCommit`). Danach blätterten B und C zweimal.

**Abweichungen von Task 4:**
1. `PagedContainer` nutzt statt `DragGesture` einen `UIGestureRecognizerRepresentable` (`UIPanGestureRecognizer`). `PageDrag` bleibt reine Logik und wird unverändert nach Plan gebaut.
2. Die Sperre `isLocked` wird im Delegate des Recognizers geprüft (`gestureRecognizerShouldBegin`), nicht nur im Container.
3. Der Seitenwechsel läuft nach Ablauf der Animation oder zu Beginn der nächsten Geste, nicht über den Completion-Handler der Animation.
4. Die Randsperre `excludesLeadingEdge` steckt im Delegate (Berührung beginnt höchstens 30 pt vom linken Rand).

**Nicht belegt (offen für Geräte- oder Folgetests):**
- Das Mitziehen der echten Nachbarseite (Spike nutzte einen Platzhalter): Ruckeln beim Neuladen nach dem Blättern und die Kosten der Vorschau sind erst mit Task 4 messbar.
- VoiceOver (`accessibilityScrollAction`): im Simulator mit XCUITest nicht prüfbar. Die Pfeiltasten in `PageArrowCapsule` bleiben der gesicherte Weg.
- Bewegung reduzieren und Haptik: nur am Gerät.
- Die Gesten wurden per XCUITest-Koordinaten nachgestellt, nicht mit einem echten Finger. Die Haltedauer-Grenzen (0,3 s) und die Geschwindigkeit liegen damit nur näherungsweise vor.

### Eigene Entscheidungen (offene Fragen des Plans)

- Fahrzeit ohne Heimadresse: kein Abschnitt für den ersten Termin (konservativ), Hinweis „ohne Heimadresse“ in der Zusammenfassung der Einstellung.
- Heimadresse wird nur gespeichert, wenn Apple Karten sie findet. Ohne Netz bleibt die alte Adresse, die Seite zeigt „Adresse nicht gefunden“.
- Ein Termin, dessen vorheriger Ort-Termin noch läuft, startet die Fahrt von zu Hause.
- Ein Online-Treffen dazwischen (ohne Ort) ändert den Ausgangspunkt nicht.
- Schaltflächen unter dem Finger lösen beim Blättern nicht aus (nur mit dem UIKit-Pan; eine `DragGesture` hätte sie ausgelöst).
- **Plausibilität der Fahrzeit (Review-Korrektur):** Kurze Ortstexte wie „Raum 2.14“, „Hörsaal A“, „Bibliothek“ oder „Mensa“ lösen in Apple Karten sonst auf einen beliebigen, weit entfernten Ort auf. Die Regeln stehen in `TravelPlausibility` (TagwerkCore) und werden in `TravelTimeService` angewendet:
  - Ein Ortstext ohne eigene Koordinaten wird nur gesucht, wenn es einen Bezugspunkt gibt: die Heimadresse mit Koordinaten, sonst das andere Ende der Fahrt mit Koordinaten. Ohne Bezugspunkt gibt es keine Suche und keinen Abschnitt. Als Bezugspunkt zählen nur Koordinaten aus dem Kalender oder der geprüften Heimadresse, nie ein anderes Suchergebnis.
  - Ein Ergebnis weiter als 50 km vom Bezugspunkt gilt als nicht gefunden: Es wird nicht gespeichert, die Fahrt bleibt ohne Wert und wird in dieser Sitzung nicht erneut gesucht (Merker je Ort und Bezugsgebiet). Bereits zwischengespeicherte Orte werden beim Lesen genauso geprüft.
  - Die Suche bekommt eine Region um den Bezugspunkt mit (`MKGeocodingRequest.region`, im SDK 27.2 geprüft; 100 km × 100 km), damit „Mensa“ die nahe Mensa findet.
  - Eine berechnete Fahrt über 180 Minuten wird verworfen: kein Wert im Cache, kein Abschnitt (auch nicht aus alten Cache-Einträgen, `TravelRules.segments` filtert zusätzlich).
  - Koordinaten aus dem Kalender werden nicht geprüft.
  - Offen: Wer weiter als 50 km von der Uni entfernt wohnt und den Ort nur als Text einträgt, bekommt keine Fahrzeit (konservativ). Alte Fahrzeitwerte aus Fehlsuchen unter 180 Minuten laufen nach 14 Tagen aus.
